# Описание проекта The Mini Compiler

## Общая концепция

`The Mini Compiler` - учебный мини-компилятор для небольшого C-подобного языка. Проект реализует полный путь компиляции: чтение исходного файла, лексический анализ, синтаксический анализ, построение AST, семантическую проверку, генерацию LLVM IR и выпуск ARM64-артефактов.

Основной сценарий работы:

1. Пользователь передает файл с программой на вход `mini_compiler`.
2. Лексер разбивает текст на токены.
3. Парсер строит AST по грамматике языка.
4. Семантический анализатор проверяет объявления, типы, область видимости и корректность управляющих конструкций.
5. LLVM-кодогенератор создает IR и, при необходимости, объектный файл `.o` или ассемблерный файл `.s` для ARM64.
6. Для тестов сгенерированный объектный файл связывается с C-харнессом `demo_main.c` и запускается через `qemu-aarch64`.

Компилятор ожидает функцию входа `compiled_fn` с одним параметром. Тестовый C-харнесс вызывает именно эту функцию.

## Поддерживаемые элементы языка

Проект поддерживает базовые элементы императивного языка:

- функции с параметрами и возвращаемым типом;
- типы `int`, `float`, `bool`, а также `auto`-вывод для объявления через `:=`;
- числовые, булевы и строковые литералы;
- переменные и присваивания;
- арифметические, логические и сравнительные операции;
- унарные операции, инкремент и декремент;
- `if` / `else`;
- цикл `for`, который в AST представлен как `WhileStmt`;
- `switch` / `case` / `default`;
- `break` и `continue`;
- вызовы функций и индексные выражения на уровне AST/грамматики.

## Архитектура компилятора

Проект построен вокруг нескольких независимых этапов:

- `main.cpp` отвечает за CLI и передает параметры в драйвер.
- `Driver` управляет пайплайном компиляции.
- `Lexer` читает исходный текст и возвращает токены парсеру.
- `Parser` строит AST из потока токенов.
- AST-модель описывает структуру программы в памяти.
- `SemanticAnalyzer` проверяет корректность программы до генерации кода.
- `LlvmCodeGenerator` преобразует AST в LLVM IR и целевые ARM64-файлы.

Такое разделение делает проект понятным: каждый этап компиляции находится в своем модуле и имеет отдельную ответственность.

## Корневые файлы

### `CMakeLists.txt`

Основной CMake-файл проекта. Задает стандарт C++17, находит установленный LLVM и собирает исполняемый файл `mini_compiler` из исходников в `src`.

Подключаемые исходники:

- `src/main.cpp`
- `src/driver.cpp`
- `src/ast.cpp`
- `src/sema.cpp`
- `src/llvm_codegen.cpp`
- `src/lexer.cpp`
- `src/parser.cpp`

Также добавляет include-директории `src` и `${LLVM_INCLUDE_DIRS}`, после чего линкует проект с `${LLVM_LIBS}`.

### `Makefile`

Альтернативный ручной способ сборки без CMake. Использует `g++`, стандарт C++17, заголовки из `src` и фиксированные пути LLVM 18:

- `/usr/lib/llvm-18/include`
- `/usr/lib/llvm-18/lib`

Цель `all` собирает `mini_compiler`, цель `clean` удаляет объектные файлы и исполняемый файл.

### `demo_main.c`

C-харнесс для интеграционного тестирования сгенерированного кода. Объявляет внешнюю функцию:

```c
extern int64_t compiled_fn(int64_t arg);
```

Затем вызывает ее с несколькими тестовыми значениями и печатает результат. Этот файл не является частью компилятора; он нужен для запуска объектных файлов, которые компилятор генерирует из тестовых программ.

### `llvm.sh`

Скрипт для установки LLVM toolchain на Debian/Ubuntu. Нужен для подготовки окружения, где доступны LLVM-библиотеки, заголовки и инструменты.

### `llvm.sh.1`

Дополнительная копия или вариант скрипта установки LLVM. Судя по имени, это вспомогательный файл, а не часть основной логики проекта.

### `mini_compiler`

Собранный исполняемый файл компилятора. Это результат сборки, а не исходный код.

### `test_app`

Собранное тестовое приложение, полученное линковкой `demo_main.c` и объектного файла, созданного компилятором. Это временный артефакт тестирования.

## Каталог `src`

### `src/main.cpp`

Точка входа исполняемого файла `mini_compiler`. Отвечает за:

- разбор аргументов командной строки;
- показ справки через `-h` или `--help`;
- выбор режима вывода: `--emit-ir`, `--emit-asm`, `--emit-obj`;
- включение трассировки через `--trace`;
- создание `Driver` и запуск `Driver::compile`.

По умолчанию компилятор генерирует объектный файл `.o`.

### `src/driver.hpp`

Заголовок центрального класса `Driver`. Описывает публичный API компилятора:

- `compile` - запускает полный процесс компиляции;
- `set_program` - принимает AST от парсера;
- `next_token` - передает парсеру следующий токен от лексера;
- `error` - регистрирует и печатает ошибки;
- `dump_ast` и `dump_ir` - отладочный вывод;
- `get_ir` - возвращает сгенерированный LLVM IR как строку.

Также хранит текущее AST, лексер, IR, список ошибок и режим трассировки.

### `src/driver.cpp`

Реализация пайплайна компиляции. Метод `Driver::compile` выполняет этапы:

1. Читает исходный файл.
2. Создает `Lexer` и `yy::Parser`.
3. Запускает синтаксический анализ.
4. При `--trace` печатает исходник и AST.
5. Запускает `SemanticAnalyzer`.
6. Генерирует LLVM IR через `LlvmCodeGenerator`.
7. При `--emit-ir` сохраняет `.ll`.
8. При `--emit-asm` или `--emit-obj` выпускает `.s` или `.o`.

Этот файл связывает все остальные подсистемы компилятора.

### `src/ast.hpp`

Описание AST - абстрактного синтаксического дерева. Содержит:

- перечисления типов (`TypeSpec`);
- перечисления операций (`BinaryOp`, `UnaryOp`, `IncDecOp`);
- базовые классы `Expr` и `Stmt`;
- узлы выражений: литералы, идентификаторы, унарные и бинарные выражения, присваивание, вызов, индексирование, pre/post increment/decrement;
- узлы операторов: блок, return, if, цикл, объявление переменной, break, continue;
- узлы `switch`, `case`, `default`;
- модель функции `FunctionDecl`;
- модель программы `Program`.

Каждый AST-узел имеет метод `dump` для отладочной печати.

### `src/ast.cpp`

Реализация методов `dump` для всех AST-узлов. Нужна для трассировки и диагностики: при запуске с `--trace` компилятор может вывести дерево программы в читаемом виде.

Файл не выполняет анализ и не генерирует код; он только форматирует AST.

### `src/lexer.hpp`

Интерфейс лексера. Класс `Lexer` хранит:

- ссылку на `Driver`;
- буфер исходного текста;
- указатели `cursor_`, `marker_`, `limit_`, которые используются сгенерированным re2c-сканером.

Главный метод `next_token` возвращает токен типа `yy::Parser::symbol_type`.

### `src/lexer.re`

Исходная спецификация лексера для `re2c`. Это первичный файл, из которого генерируется `src/lexer.cpp`.

Лексер распознает:

- пробелы и комментарии `//`;
- ключевые слова `func`, `return`, `var`, `if`, `else`, `for`, `switch`, `case`, `default`, `break`, `continue`;
- типы `int`, `float`, `bool`;
- булевы литералы `true` и `false`;
- операторы `:=`, `=`, `+=`, `-=`, `++`, `--`, `==`, `!=`, `<=`, `>=`, `&&`, `||`, арифметические и логические символы;
- скобки, запятые, точки с запятой и двоеточия;
- целочисленные, вещественные и строковые литералы;
- идентификаторы.

При неизвестном символе лексер сообщает ошибку через `Driver::error`.

### `src/lexer.cpp`

Сгенерированная реализация лексера на основе `src/lexer.re`. Используется при сборке компилятора. Обычно этот файл не редактируют вручную: изменения лучше вносить в `lexer.re`, затем регенерировать `lexer.cpp`.

### `src/parser.y`

Исходная грамматика парсера для GNU Bison C++ skeleton `lalr1.cc`. Это первичный файл, из которого генерируются `src/parser.cpp` и `src/parser.hpp`.

Грамматика описывает:

- структуру программы как набор функций;
- параметры функций;
- возвращаемые типы;
- блоки и списки операторов;
- объявления переменных через `var name type = expr` и `name := expr`;
- выражения с приоритетами операций;
- `if` / `else`;
- цикл `for`;
- `switch` с `case` и `default`;
- `return`, `break`, `continue`;
- литералы, идентификаторы, вызовы и индексирование.

В semantic actions создаются объекты AST через `std::make_unique`.

### `src/parser.hpp`

Сгенерированный Bison-заголовок парсера. Содержит типы токенов, объявления класса `yy::Parser` и интерфейс, который используют `Driver` и `Lexer`.

Обычно не редактируется вручную.

### `src/parser.cpp`

Сгенерированная Bison-реализация парсера. Выполняет синтаксический анализ и вызывает semantic actions из `parser.y`.

Обычно не редактируется вручную.

### `src/sema.hpp`

Интерфейс семантического анализатора. Описывает класс `SemanticAnalyzer`, который проверяет программу после парсинга и до генерации LLVM IR.

Основные задачи:

- проверка объявления переменных перед использованием;
- проверка типов операндов;
- проверка уникальности значений `case` в `switch`;
- проверка допустимости `break` и `continue`;
- вывод типов для `auto`-переменных, объявленных через `:=`;
- сбор информации о функциях и проверка точки входа.

### `src/sema.cpp`

Реализация семантического анализа. Содержит:

- стек областей видимости;
- таблицу символов;
- коллекцию функций;
- стек контекстов для циклов и `switch`;
- проверки совместимости типов;
- проверку объявлений и присваиваний;
- анализ выражений и операторов;
- специальную логику для `switch` / `case` / `default`.

Также проверяет наличие функции `compiled_fn` с одним параметром.

### `src/llvm_codegen.hpp`

Интерфейс LLVM-кодогенератора. Описывает:

- `LlvmCodeGenerator::generate` для генерации LLVM IR;
- `write_ir_file` для записи `.ll`;
- `ir_string` для получения IR в виде строки;
- `emit_target_file` для выпуска `.s` или `.o`;
- `TargetFileKind`, который выбирает между Assembly и Object.

### `src/llvm_codegen.cpp`

Реализация генерации LLVM IR и целевых ARM64-файлов. Использует LLVM API:

- `LLVMContext`;
- `Module`;
- `IRBuilder`;
- `Verifier`;
- `TargetMachine`;
- `legacy::PassManager`.

Файл задает целевую архитектуру:

```cpp
static constexpr const char *TARGET_TRIPLE = "aarch64-unknown-linux-gnu";
```

Кодогенератор создает функции, базовые блоки, локальные переменные, выражения, условные переходы, циклы, `switch`, `break`/`continue` и возвращаемые значения. Для переменных используется стек областей видимости, а для циклов - стек целей перехода.

### `src/Makefile`

CMake-сгенерированный Makefile внутри каталога `src`. Это артефакт сборки, а не ручной исходный файл проекта. Его не стоит редактировать вручную.

### `src/CMakeCache.txt`, `src/cmake_install.cmake`, `src/CMakeFiles/`

Служебные файлы CMake, ошибочно или временно созданные внутри `src`. Они относятся к состоянию сборки и не являются исходным кодом компилятора.

### `src/*.o`

Объектные файлы, полученные при компиляции отдельных `.cpp`. Это бинарные артефакты сборки.

## Каталог `tests`

### `tests/run_tests.sh`

Интеграционный тестовый скрипт. Для каждого тестового `.txt` файла:

1. запускает `./mini_compiler` с `--emit-obj`;
2. линкует полученный `.o` с `demo_main.c` через `aarch64-linux-gnu-gcc`;
3. запускает результат через `qemu-aarch64`;
4. извлекает вывод для `compiled_fn(3)`;
5. сравнивает результат с ожидаемым значением.

Покрывает базовый end-to-end сценарий: исходный код -> объектный файл -> линковка -> запуск.

### `tests/test_factorial.txt`

Тестовая программа на мини-языке. Реализует функцию `compiled_fn`, которая считает факториал аргумента с помощью цикла `for`.

Для `compiled_fn(3)` ожидаемый результат в тестах - `6`.

### `tests/test_sum_squares.txt`

Тестовая программа, которая считает сумму квадратов чисел от `1` до `arg`.

Для `compiled_fn(3)` ожидаемый результат - `14`, потому что `1 * 1 + 2 * 2 + 3 * 3 = 14`.

### `tests/test_switch.txt`

Тестовая программа для проверки `switch` / `case` / `default`. Возвращает:

- `10` для `arg == 1`;
- `20` для `arg == 2`;
- `30` для `arg == 3`;
- `0` для остальных значений.

Для `compiled_fn(3)` ожидаемый результат - `30`.

### `tests/test_switch.o`

Объектный файл, сгенерированный из `tests/test_switch.txt`. Это артефакт тестирования, а не исходный тест.

## Каталог `build`

Каталог `build` содержит результаты CMake/Ninja-сборки:

- `build/CMakeCache.txt` - кэш конфигурации CMake;
- `build/cmake_install.cmake` - служебный install-скрипт CMake;
- `build/build.ninja` - Ninja-файл сборки;
- `build/.ninja_deps` и `build/.ninja_log` - внутренние файлы Ninja;
- `build/CMakeFiles/` - служебные файлы CMake, зависимости, логи, правила и объектные файлы;
- `build/generated/lexer.cpp` - копия или сгенерированная версия лексера;
- `build/generated/parser.cpp` - копия или сгенерированная версия парсера;
- `build/generated/parser.hpp` - сгенерированный заголовок парсера.

Эти файлы нужны для локальной сборки, но не являются основной логикой проекта.

## Сгенерированные файлы

В проекте есть файлы, которые являются результатом генерации:

- `src/lexer.cpp` генерируется из `src/lexer.re`;
- `src/parser.cpp` и `src/parser.hpp` генерируются из `src/parser.y`;
- файлы в `build/generated/` являются сборочными копиями или результатами генерации;
- объектные файлы `.o` и исполняемые файлы являются результатами компиляции.

Для изменения синтаксиса языка лучше редактировать `src/parser.y`, а не `src/parser.cpp`. Для изменения лексических правил лучше редактировать `src/lexer.re`, а не `src/lexer.cpp`.

## Как собрать

Основной путь через CMake:

```bash
cmake -S . -B build
cmake --build build
```

Альтернативный путь через Makefile:

```bash
make
```

Для ручного Makefile требуется, чтобы пути к LLVM 18 соответствовали локальной системе.

## Как запустить

Пример компиляции тестовой программы в объектный файл:

```bash
./mini_compiler tests/test_switch.txt --emit-obj
```

Пример вывода LLVM IR:

```bash
./mini_compiler tests/test_switch.txt --emit-ir
```

Пример генерации ARM64 assembly:

```bash
./mini_compiler tests/test_switch.txt --emit-asm
```

Пример запуска с трассировкой этапов:

```bash
./mini_compiler tests/test_switch.txt --trace
```

## Как запустить тесты

```bash
./tests/run_tests.sh
```

Тесты ожидают наличие:

- собранного `mini_compiler`;
- `aarch64-linux-gnu-gcc`;
- `qemu-aarch64`;
- рабочего LLVM/ARM64 toolchain.

## Итог

Проект демонстрирует базовую архитектуру компилятора с понятным разделением на frontend, semantic analysis и backend. Он подходит для изучения устройства компиляторов, расширения грамматики языка и экспериментов с LLVM-кодогенерацией под ARM64.
